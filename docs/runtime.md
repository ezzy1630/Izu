# Optional execution runtime

The native engine owns source, revisions, checkpoints, recovery objects and workspace registration. It works without a daemon or runtime. `izu-runtime` adds an explicitly selected local command, a bound workspace, admission accounting, process ownership and a durable job registry.

Every command has a registered engine workspace ID, exact expected head and working tree, canonical directory identity, explicit argv, environment policy, resource request and deadline. Binding and admission recheck the source tree. Launch verification captures through the source directory pinned by the engine writer lease. A managed writer starts at its selected private cwd before its first source write. The runtime does not discover or execute repository recipes, insert a shell, select the human source root implicitly, or manage credentials. An explicitly selected shell remains an explicitly selected executable.

`RuntimeConfig::new(worker_executable)` selects a trusted Rust worker. The CLI sets `worker_prefix` to `["__runtime-worker", "--ticket"]`; the runtime appends an absolute ticket path. The worker runs in a fresh owned process group. It waits for a control-pipe handshake after the parent durably records its source lease token and running PID. The handshake binds the independently observed job-directory device/inode and job ID. The worker validates its actual cwd descriptor and the selected child inherits that directory without another path-based chdir.

The worker observes the command exit, durably publishes its result and retains the group leader until cleanup. The shared process layer signals the owned group before reaping and checks group absence within a bounded deadline. The runtime clears the engine writer intent only when cleanup reports both leader reaping and observed group absence, and the source locator still identifies the bound directory. A replaced source root retains unknown ownership, its reservation and durable intent. A missing result, failed cleanup or failed intent clearance cannot produce passing check evidence. This protocol controls cooperating processes; it does not contain a program that changes session/group or an unrelated editor under the same Unix user. On controller EOF the worker kills its group; selected commands cannot rely on a SIGTERM handler running.

Every intent-clearance branch compares the held source-directory descriptor with the current source locator. This includes prelaunch setup failures, failed registry publication and fallback cleanup during `Runtime::drop`. Failure to read the registry cannot bypass source identity validation. Explicit operator recovery remains a separate exact-token acknowledgement.

The engine's separate live-writer lease excludes native restore, undo, close and environment materialization while a managed command runs. Source capture, checkpoint and metadata commits use a different lock, so a selected child can invoke native metadata commands without deadlocking its controller. The durable writer intent survives controller crashes and dropping the OS lease. Independent native materialization also refuses that intent until its exact token is explicitly reconciled.

The default admission budget allows four running jobs, eight CPU slots, 8 GiB of memory reservations, 20 GiB of disk reservations, 32 open managed workspaces, 128 queued jobs and 4,096 retained job records. These values are configurable and persisted in the shared registry; controllers with a different budget are rejected. Requests exceeding the entire budget fail before admission. Queued jobs can be cancelled without starting a writer; jobs on one workspace serialize. Unknown writers keep their original reservations.

Running-job and queue limits are enforced by the runtime. CPU slots, memory and disk are reservation accounting. They are not OS quotas. Ports are cooperative claims with a localhost IPv4 bind probe; releasing the probe before command launch permits an external bind race. Hard CPU/memory/disk limits, race-free socket handoff and security containment are reported unsupported. A command can exceed its reservation or create unmanaged processes. Thirty private workspaces can exist while only four admitted commands run.

The registry uses version 1 bounded JSON, a shared transaction lock and per-job controller leases, private owned directories/files, descriptor-relative no-follow operations and the platform persistence barrier. Immutable source objects remain the engine's format. Registry state records ordered job identities, workspace bindings, commands, environment key names, optional native environment Blob and starting-file receipt, reservations, state, output and writer tokens. The schema is independent of Rust memory layout. Unsupported versions, corrupt identities, oversized input and non-regular files fail explicitly. A post-rename persistence failure reports uncertainty; the runtime requires reopen before further actions.

Opening a registry checks the parent, registry and job-artifact filesystems and refuses known volatile storage before acknowledging any job state. For example, a Linux tmpfs registry returns `RuntimeError::Unsupported`. This classification cannot prove persistent hardware beneath every otherwise ordinary filesystem.

Overlay values remain in the in-memory launch request and a private launch ticket. They are omitted from returned and durable job metadata. Tickets expire after completion, failed launch and registry recovery. Inherited environment values are not serialized. Environment inheritance and same-user filesystem/process access do not separate credentials. Command argv and captured stdout/stderr may themselves contain secrets selected or printed by the command; the runtime does not invent redaction that changes the evidence.

Each stdout/stderr stream retains a configured bounded prefix, 64 KiB by default, and reports dropped byte counts while draining its pipe. Command deadlines begin at the release handshake, after durable admission and launch setup. The worker enforces its own monotonic deadline while the command runs; a parent fallback permits at most ten seconds for a delayed durable completion report before initiating bounded cleanup. A live foreign snapshot has no claimed absolute execution deadline; the owning controller can report the actual release deadline. Cancellation cleanup is bounded; failure to observe safe cleanup becomes unknown ownership. Output is an observation of the actual command, not proof of successful source checks or deployment.

Independent CLI processes can open the same registry. Before admission, each controller reloads the shared state under a transaction lock. A held per-job OS lease identifies a live foreign controller: its queue is preserved and its running reservations remain counted. The lock durably grants Starting reservations, then releases before source lease/capture/ticket preparation. A short Running publication precedes the release handshake. Starting, Running and Unknown jobs all count toward the shared budget. Registry transactions do not hold a lock for the command lifetime. Cross-controller FIFO fairness is not promised. Cancellation and shutdown only signal handles owned by the calling controller.

Managed new/resume preparation, post-command checkpoints and runtime close acquire a separate `SourceOperationPermit` before native history mutation. At most `min(max_running_jobs, 4)` source operations proceed across cooperating controllers; four is the source-operation concurrency ceiling, separate from the configured running-job budget. This prevents source setup and completed controllers' multi-operation closes from creating an unbounded queue at the native history lock. Native publication retains its ten-second lock-acquisition bound and all closure hashing, persistence and identity checks. Command admission still counts Starting, Running and Unknown jobs independently.

Source permits use private permanent `source-N.lock` names in the registry, descriptor-relative no-follow opens, file/directory binding checks and process-held locks. Newly created coordination entries are persisted under a short registry transaction. Waiting holds neither that transaction nor a native history lock. Dropping the permit or process death releases the grant; coordination names are never unlinked by the runtime. A grant is no history or job acknowledgement. The managed facade releases it before submitting or waiting for a command, then reacquires for its final checkpoint. Close holds it through source verification, checkpoint, final recovery capture, unregistering and acknowledgement. Like queued-job waiting, source admission waits for capacity or cancellation; it does not consume the command execution timeout, which starts at the release handshake. There is no cross-controller FIFO promise or OS resource containment.

New managed starts retain the engine's exact workspace-fork receipt. If preparation fails before its first checkpoint, the partial response includes the created workspace, retained path and `fork_operation`. It identifies any newer engine-reported uncertain operation in preference to the fork. After checkpoint, failures retain that checkpoint or a newer engine-reported operation. Neither cancellation nor an incomplete start implies rollback; current HEAD is never substituted for the exact fork receipt.

After a controller lease is lost, every Starting job, prior running jobs and queued jobs with a durable writer token become `OwnershipUnknown`. Unadmitted queues that had not acquired writer intent become cancelled before launch. A Starting job may have a source intent whose token was not yet published to the runtime; it stays Unknown and cannot adopt an intent by workspace ID alone. An operator must inspect and acknowledge the exact engine token before reconciling that runtime record. Recovery never signals a saved PID. `acknowledge_stopped(job_id, note)` is an explicit operator assertion, distinct from observed shutdown; it reconciles only the job's exact matching engine token and refuses an unrelated intent. Unknown ownership blocks runtime close. Runtime and native history recovery do not silently clear it.

A normal close stops and reaps owned writers, checkpoints eligible source through the engine, reads back the exact receipt/tree, closes through the engine and reads back the close operation. It unregisters the workspace and retains its directory and immutable history. The engine also retains a final recovery capture including ignored source within its limits. The runtime never recursively deletes workspace files, generated/ignored data, database files or an external database. A source capture is not a database-consistent backup or filesystem-wide snapshot.

Close retains the persisted runtime directory binding after a worker finishes. A replaced bound source is rejected before checkpointing or unregistering it, even when the replacement carries the original workspace marker. Identity is checked again after checkpoint and close; a change after a visible operation reports uncertainty with that operation's identity for recovery.

After a checkpoint is acknowledged, any close failure, including cancellation, failed readback or runtime registry acknowledgement, reports publication uncertainty with a typed operation identity. The identity is the checkpoint operation until the engine reports a later visible recovery or close operation. Callers can obtain it through `RuntimeError::uncertain_operation()` and inspect that exact operation with a fresh cancellation token before deciding whether to retry. Prepublication cancellation and stale-source refusal retain their ordinary errors. Close does not roll back visible history or delete retained source on these failures.

Candidate checks execute from a fresh private workspace materialized at the candidate's exact result revision and tree. The engine publishes a durable pending attempt before execution, invalidating an older pass. Terminal evidence preserves that attempt ID and start time, exact command and input identities. Missing, crashed, cancelled, failed and source-changing attempts cannot reuse earlier passing evidence. Source directory identity is checked before and after the final source capture. A source-changing check records failure even if its process returned zero. A substituted root is not captured or closed, and its original and replacement files stay registered for explicit recovery.

`CheckSpec.environment = None` means the environment is unknown. It is not fixture, dependency, toolchain or credential attestation. `Some(id)` names a native Blob containing a versioned environment binding of at most 1 MiB. The native Blob ID is distinct from the prepared-cache key. The binding includes exact recipe/source identity and verified manifest; it does not carry a cache locator or raw preparation argv. The cache is selected at the repository's `.izu/environments/v1` directory.

The check helper materializes private dependency and warm-output files into its fresh candidate workspace before acquiring the managed writer lease. At admission, the environment verifier uses that lease's pinned source directory to rehash actual private file contents, modes, symlink targets and lockfiles, compare the exact manifest and capture source before and after verification. Its opaque proof retains a shared cache lease through owned process cleanup. A serialized starting-file receipt is durably published before any worker release; a bound pass requires that receipt to match the requested native binding, workspace, source and manifest. A malformed binding, missing cache, partial materialization or tampered private dependency fails explicitly and keeps the pending attempt from reusing an older pass. Files and workspace registration remain available after preparation failure.

The receipt's scope is `StartingFileContents`. Commands can mutate writable warm outputs after this observation. OS and architecture are observed; ABI and toolchain identity remain explicit caller declarations. The receipt does not attest executing binaries, databases, remote fixtures, credentials or immutability during execution. Recipe parsing, import and materialization never autoexecute preparation commands. `poll_with_cancel` and `wait` propagate cancellation into source and starting-environment verification.

From the repository root, reproduce the process and recovery checks with the pinned Rust toolchain and an explicit owned scratch directory:

```sh
mkdir -p .artifacts/tmp
TMPDIR="$PWD/.artifacts/tmp" cargo test --locked -p izu-runtime
```

Tests launch real commands and descendants, enforce actual admission, test bounded logs, port collisions and cancellation, preserve 30 private writer outputs and launch 30 independent controller processes under a shared four-job budget, exercise replaced paths/FIFOs/publication uncertainty, kill a real controller and prove an independent source restore remains blocked while a finite escaped writer continues, and reject recovery of another writer token. Passing repository tests provide local evidence only; integrated CLI, deployment and remote behavior require their own evidence.

The `runtime-overhead` example measures direct and managed serial `/usr/bin/true` launches at the same private cwd. It includes admission, source verification, writer intent, the worker, durable completion and cleanup; source setup/fork and final close are excluded. Supply an absolute, previously absent artifact directory and the exact built worker path. The example leaves its source, workspace, native history and `metrics.json` available for inspection. A historical three-run macOS debug sample on Neural measured a 1.61 ms direct mean and 2,983.59 ms managed mean before the shared store's batch publication changes. The individual managed runs ranged from 1,857.83 to 4,070.61 ms. These historical timings do not measure the current source or final integrated release. This small local sample measures durable workflow overhead, not an OS scheduler benchmark or a general performance guarantee.
